# 安全的自主行动 · Agent 设计说明

> 面向 Fellowship 命题:*"在你选择的 ERP 场景中,选取一个需要 Agent 主动调用工具、修改数据或推动业务流程的环节。构建能够安全完成自主行动的系统。"*

本原型选取的场景是 **跨境员工调动** —— 从中国上海到沙特利雅得的一次国际调派,横跨员工、HRBP、IT 三个角色。Agent 需要在流程中主动做很多事情:识别关键字段变更、路由专业人员、诊断身份异常、拉起下游任务。这些动作里的每一个,都涉及"能不能做"和"该不该做"两个问题。

本文说明这套 Agent 的**安全护栏是如何设计的** —— 为什么不新造权限层,而是嫁接在 SF 现有的平台机制上。

---

## 一、核心主张:Agent 不引入新权限层

大多数 AI Copilot 演示,权限护栏是自己发明一套 —— 常见做法是在 system prompt 里写"你不能查看 X,不能修改 Y"。这本质上是 **LLM 层的软约束**:模型可以违反、不可审计、随着 prompt 漂移。

本原型的主张是相反的:

> **Agent 的自主行动完全落在当前会话用户在 SF 中已被授权的边界内。**
> 用户看不到的字段,Agent 拉不到;
> 用户不能改的对象,Agent 不能替他改;
> 用户不能去的页面,Agent 不能跳过去。

这不是"AI 少做一点",而是让 **AI 的行动边界与业务系统的授权边界完全对齐** —— 前者是后者的严格子集。这样"Agent 能做什么"这个问题,不再由 prompt 决定,而由 SF 的配置决定;不再由 AI 团队负责,而由已经存在的授权治理团队负责。

---

## 二、主轴:RBP(Role-Based Permissions)

**RBP 是 SF 的核心授权引擎** —— 它决定了一个用户能看到哪些员工、能读写哪些字段、能触达哪些工作流。在本原型的三个角色页里:

- **员工林晨**看到的岗位机会、自己的候选人档案、申请追踪 —— 都来自她所属的 Employee Central 数据范围
- **HRBP Mira**看到中东区的调动请求队列、影响审查清单、审批流 —— 来自她在 RBP 中被授予的中东区 HRBP 角色
- **IT 管理员 Tom**看到的告警队列、依赖图、诊断视图 —— 来自 IT 身份团队角色

Agent 在每个视图里的"知道"和"能做",都被限定在**当前会话用户的 RBP 权限内**:

| 场景 | RBP 边界的体现 |
|---|---|
| 员工向 HR 发信号 | 员工的原话保留在员工个人记录里(她自己的 RBP 域);HRBP 端只看到抽象化的信号提示 —— **Agent 不做跨角色破墙** |
| HRBP 修改生效日期 | 触发关键字段变更 · 使 v1 签署失效 · 通知 3 位有相应审批人角色的用户重新确认 —— **Agent 只能通知,不能替他们签字** |
| IT 遇到身份映射不明 | Agent 观察到多条候选记录 · 路由至身份治理团队角色 —— **Agent 不做关联判断、不闭环告警,因为它不持有治理决策权限** |

**关键点:这些边界不是 Agent 自己"想通"的,而是它必须查询 SF 授权系统才能采取任何行动。**任何越界的动作都会因为找不到授权而失败 —— 与人类用户在 SF 里遇到"没权限"是同一套机制。

---

## 三、支撑机制之一:Document Grounding

RBP 决定 Agent 能触达哪些**对象**;Document Grounding 决定 Agent 呈现给用户的**依据**从哪里来。

### 设计原则

- **无来源不呈现**:Agent 不基于训练语料生成推荐 —— 它只在被授权可访问的 SF 对象、文档、既往记录中检索
- **来源可见**:每条呈现给用户的"依据"都带来源标签(system / self-report / unverified) —— 让人看到 Agent 引用的是权威记录、员工自述、还是无来源的推测
- **无来源就说无来源**:如果检索不到,Agent 明确说"记录里没有,不等于事实上没有"

### 在演示中的体现

- 员工"经历对照"卡:每条匹配都有 `srcLabel` + `period`,标注是从 CRM 系统、Learning Hub 认证系统、还是员工自述里读到的
- HRBP 影响审查清单:每一项的"待处理/已核实/阻塞"状态都写明所依据的对象和 owner
- IT 诊断卡:Agent 只呈现观察结论("自动身份映射返回了多条候选记录"),不做因果推断("这是冲突")—— 因为后者需要它没有的治理判断权

### 为什么这条重要

它防止的是 AI 最常见的失败模式 —— **"看起来合理的编造"**。跨境调动涉及合规、隐私、税务、担保等专业域,一个自信但无来源的建议可能让 HR 直接踩雷。Document Grounding 让 Agent 有一根锚:**没数据,就不发言**。

---

## 四、支撑机制之二:Navigation(路由配置)

RBP 是"看得见什么、能改什么"的边界;Navigation 是"能去哪里"的边界。

### 设计原则

- **Agent 的"下一步"必须落在平台已配置的路由目的地上** —— 它不能跳过某个未开放的中间态,不能把用户送到某个自己"觉得合适"的页面
- **每次 Agent 建议"跳转",跳的都是 SF 中已经存在的路由**(在原型里表现为 hash-based 的 view id · 由每个角色的 STEPS 常量声明)
- **暂停点是明示的**:当 Agent 判断下一步归他人处理时,它不"退出对话",而是路由到"待 X 处理"的显式视图,并明确谁是接手方

### 在演示中的体现

三处刻意的暂停,都不是 Agent"没词了",而是 **Agent 主动把控制权交给平台配置里已经存在的下一站**:

- 员工"分析岗位":Agent 展开利弊后,路由到 `focus-match`(经历对照)或 `goto-prep`(面试准备)—— 都是员工角色下的已授权视图
- HRBP"路由专业人员":Agent 生成推荐后,操作按钮触发的是 SF 里既有的"派发工作流"路由 —— 不发明新的操作路径
- IT"身份治理案例":Agent 触发的是"路由至治理团队"的既有流程,而不是"标记已解决"

### 为什么这条重要

它防止的是另一种失败模式 —— **"AI 造出一个不存在的操作"**。当 Agent 说"我帮你提交合规审查了",如果背后没有一个真实存在、被授权的、可追溯的路由,那这只是对话记录里的一段字,不是一个业务动作。Navigation 配置让 Agent 的每个动作都必须**能被业务系统识别、能被审计日志记录、能被后续追踪**。

## 五、风险分层响应机制

在上面三层护栏之上,Agent 对不同风险等级的场景采取不同的自主度:

| 风险等级 | 判定标准 | Agent 响应 |
|---|---|---|
| **低** | 不改变任何业务状态 · 仅读取当前用户 RBP 域内数据 | 直接完成 · 不需要人拍板 |
| **中** | 触发既有签署失效或产生新对象 · 但仍在当前用户授权范围内 | 自主执行"检测 · 通知 · 生成新版本"的机械步骤 · 但**关键决定(如重新签署、拍板派发)必须由持有相应角色的人做出** |
| **高** | 涉及跨专业域的判断(合规 / 隐私 / 身份治理 / 跨境法律) · 或当前用户不持有该判断权限 | Agent **拒绝自动化解决** · 只观察、只描述、只路由 · 明确告知 "已路由 ≠ 已关闭" · 下游流程保持暂停直到有资质的团队回执 |

### 判定为什么这么划

这个分层的依据不是任意的:

- **中风险的锚点是"是否触发既有签署失效"** —— 因为这标志着有既定的人类审批人需要被通知
- **高风险的锚点是"决定是否属于当前角色的判断权限之外"** —— 这直接可以由 RBP 查询回答:此用户是否拥有 X 决定的权限?没有,即高风险

**因此,风险分层可以从 SF 配置直接推导 —— 不需要 Agent 层再维护一份风险规则表**。这一点是 RBP 作为主轴带来的最大工程红利。

## 六、完整的自主行动闭环

以 HRBP 修改生效日期为例,把上面所有机制串起来看 Agent 的一次完整行动:

```
1. 理解目标   HR 修改了 effectiveDate 字段(检测器识别为关键字段)
2. 检查权限   RBP 查询 · 当前用户是否有权修改该员工记录的此字段?
                    ├── 无 → 拒绝 · 返回权限错误(与人类操作行为一致)
                    └── 有 → 继续
3. 拉取上下文  Document Grounding · 检索:v1 由谁签署?哪些流程与该字段有依赖?
4. 风险判定    触发 v1 失效 → 判定为中风险 → 需要通知既有签署人重新确认
5. 自主执行    机械步骤 · Agent 完成:
               ├── 使 v1 状态置为 invalidated
               ├── 生成 Move Request v2 草稿
               └── 通知 3 位审批人(通过既有 route 配置,不越权替签)
6. 展示与暂停  Navigation 路由到"审批流"视图 · 显式暂停等待人类确认
7. 记录结果    动作写回业务对象(不藏在对话记录里) · 可审计
```

每一步都锚定在平台机制上:第 2 步锚在 RBP、第 3 步锚在 Document Grounding、第 6 步锚在 Navigation。**Agent 只是把这些既有机制串起来,让它们协同,以推动流程前进 —— 而不是发明新的权限、发明新的知识、发明新的路径。**

---

## 七、这个设计解决了什么、独到之处

### 解决的问题

- **AI Copilot 的权限护栏通常是软约束**(prompt 里写"你不能"),不可审计、易漂移、跨团队难协作
- **AI 编造建议的失败模式没有制度化的防御**,只能靠人工事后核查
- **"AI 自主行动"和"人类审批"之间没有清晰的划界规则**,常常是"能自动就自动"的偷懒心态

### 为什么本设计是对的

- Agent 的边界与业务系统的授权边界严格对齐 —— **可以直接沿用现有的 IT 治理和合规审计机制**,不引入新的治理开销
- Agent 的建议依据可追溯 —— **每一条推荐都能回答"你凭什么这么说"**
- Agent 的动作可路由、可审计 —— **每一个业务动作都是一个真实存在的 SF 流程,而不是对话里的一段文本**

### 独到之处

**风险分层的判定标准与 SF 平台机制同源**:中风险 = 触发签署失效(既有工作流可查询);高风险 = 当前用户无相应决策权限(RBP 可查询)。

这意味着:**当客户在 SF 里调整了 RBP 或工作流配置,这个 Agent 的行为边界会自动跟着调整,不需要重新训练模型、不需要重写 prompt、不需要开会重新对齐 —— 这是"嫁接在平台上"和"外挂在平台旁"的根本区别。**
